# Nav2 integration with Lite3 limits, terrain hazards and proximity lock (2026-11-13)

## What was added (no university file modified)

- **`params/nav2_lite3.yaml`.** Generated by `tools/make_nav2_params.py` as the
  university `nav2_params.yaml` plus an explicit, tested patch list. The diff
  against the university file contains exactly these patches:
  - MPPI is capped at vx 0.10 m/s, vx_min 0 (no reversing), vy 0 and wz 0.20
    rad/s, with low accelerations.
  - The velocity smoother is capped at [0.10, 0, 0.20] forward and [0, 0, −0.20]
    minimum.
  - The behavior server runs only `spin` and `wait`, at ≤ 0.20 rad/s.
  - Both behavior trees are replaced by copies of the Humble defaults with the
    `BackUp` recovery removed, because the LiDAR can't see behind the robot.
  - Both costmaps get `/lite3_terrain/hazards` as an extra observation source,
    with `expected_update_rate: 0.5`. A stale hazard feed makes the costmap
    non-current, which stops the controller.
  - `python3 tools/make_nav2_params.py --check` detects drift from the university
    file.
- **`params/twist_mux_locks.yaml`.** Loaded together with the university
  `twist_mux_topics.yaml`. Lock `terrain_stop` (priority 50) blocks navigation
  (priority 10) while `/lite3_terrain/stop` is true, or when that topic has been
  silent for more than 0.5 s. The joystick (priority 100) is never blocked.
- **`terrain_monitor` publishes `/lite3_terrain/stop`.** It is true when an
  obstacle or drop is ≤ 0.60 m ahead in the corridor or ≤ 0.45 m around the
  robot, or when its inputs are invalid. It stays true for 1 s after clearing.
- **`launch/navigation.launch.py`.** It starts the university
  `lite3_bringup.launch.py` and `lite3_navigation.launch.py` (SLAM by default)
  with the generated parameters, plus `terrain_monitor` and `twist_mux`. **The
  mux output defaults to `/lite3_locomotion/dry_cmd_vel`.** Driving `/cmd_vel`
  requires both `mux_output:=/cmd_vel` and `allow_robot_motion:=true`; otherwise
  the launch refuses.

## Blocker found: sensor link degradation

During the dry run, sensor delivery from the robot-side bridge degraded:

- `/livox/points` (best effort, 440 KB per cloud) fell from 10 Hz to 2 Hz, with
  gaps up to 3.5 s.
- Fast-LIO `/odom` showed a 16.6 s gap.
- Small 200 Hz telemetry showed 0.59 s gaps.
- **The degradation persisted with all of our processes stopped,** so it is
  outside this computer: network, bridge host, or other load on the shared robot.

The fail-safes responded as designed: the costmap reported the hazard feed
stale, and the lock timeout would block navigation. But autonomous motion is
not possible on such a link, and the movement-test readiness check (telemetry
≤ 0.25 s old) would refuse to start.

Tried and rejected as a workaround:

- Subscribing to the reliable `/livox/lidar` `CustomMsg` from Python: only about
  3 Hz of throughput, because deserializing 20k points per message is too slow.
- Fast-LIO's local `/cloud_registered_body`: it inherits the same input gaps,
  plus a 0.5 m blind radius and 1/3 point decimation.

## Next steps

1. Restore a stable link (≥ 9 Hz clouds, telemetry gaps < 0.25 s) and find the
   cause with the lab: bridge host load, Wi-Fi versus Ethernet, other users.
   Re-measure with the probes from this session.
2. With a stable link, repeat the dry run for several minutes and confirm no
   hazard staleness.
3. Then a physical step: stand the robot with the movement framework, run
   `navigation.launch.py mux_output:=/cmd_vel allow_robot_motion:=true` inside an
   authorized session, and send single 1 m goals.

   This needs one additional framework piece first: a `nav_goal` step type, so
   the runner's geofence, tilt, staleness and takeover monitoring wrap Nav2-driven
   motion. The runner's command-path health check currently (correctly) rejects
   the extra `twist_mux` publisher on `/cmd_vel`.

## Physical mode (added 2026-11-16, not yet run on the robot)

`navigation.launch.py mux_output:=/cmd_vel allow_robot_motion:=true` (started only by
`operator/start_navigation.sh --physical`, typed ARM) also loads
`params/twist_mux_physical.yaml`:

- **`operator_hold` lock (dead-man).** Topic `/lite3_ops/hold`, timeout 0.5 s,
  priority 50. Nothing below priority 50 passes unless a supervising
  `lite3_movement_tests` runner publishes `false`. The runner does this only from
  its safety-check loop. A fresh mux that has never received the topic is locked.
- **`test_cmd` input.** Topic `/lite3_ops/test_cmd_vel`, priority 20. Bounded test
  moves; blocked by both locks.
- **`safety_stop` input.** Topic `/lite3_ops/stop_cmd_vel`, priority 255. Zero
  velocity only, so a commanded stop passes every lock instead of relying on
  silence.

`check_mux_lock.py --physical` verifies all of this on the real twist_mux binary in
an isolated domain (PASS). `terrain_monitor` gained `stop_ahead_m` / `stop_radius_m`
ROS parameters. They can be raised for a test but are refused below the validated
defaults (0.60 m / 0.45 m from the centre). The physical tests (M0–M9),
their PASS criteria and the readiness checklist are in
[operator/PHYSICAL_TESTS.md](../../../operator/PHYSICAL_TESTS.md). They are
implemented as navigation step types in `lite3_movement_tests` (`nav_steps.py`),
which closes next step 3 above.
